# ステップ2 描画改善案（ビジュアル担当）

前提: ステップ1の実装（src/render/render.ts）は「心地いい」評価。黒は 0 のまま保つ（背景に光を足す案は入れない）。以下、優先度順。

## 1. ボールの軌跡をジオメトリで描く（残像に頼らない）【最優先】
- **狙い**: 今の尾は AfterimagePass 頼み。最高速 V_REF≈1740px/s だと 60fps で 1 フレーム 29px 動くので、直径 10px のボールの尾が「数珠」状に途切れる。さらに残像は画面全体にかかるので、線のフラッシュまで尾を引いて濁る。軌跡は物理の履歴から線として描き、途切れない尾にする。
- **仕様**
  - 長さ N=30 ステップ（0.25s）。2 ステップおきに k=0,2,…,30 の点を取り、隣り合う点を太さのあるクアッドでつなぐ（1球あたり 15 本）。先頭は補間済みの現在位置につなぐ
  - 太さ `w_k = 2r·(0.8 − 0.6·k/N)`、強度 `I_k = I_ball(rs−k)·0.6·(1−k/N)^1.5`
  - `I_ball(s)` は「ステップ s 時点」のボール強度（既存の `0.55 + (1+1.5v)e^(−t/0.09)`）。こうすると、衝突点の明るさが尾の上にしばらく残って流れていく
  - 色はボールと同じ（ballLook の音程色、または OFF_WHITE）。通常時は bloom の閾値 0.8 未満になり、光るのは衝突直後だけ
  - afterimage の既定値を 0.88→0.80 に下げる（波紋や線がふわっと消える役だけ残す）。GUI に `trail: 'geometry'|'afterimage'` を追加して A/B 比較できるようにする
- **変更箇所**: render.ts に `trails` InstancedMesh（PlaneGeometry、上限 MAX_BALLS×15=3000）と `drawTrails(sim, rs)` を追加。`drawBalls` の強度計算は `ballIntensity(look, step)` に切り出して共用する。main.ts には GUI 項目を足す
- **性能**: draw call +1。毎フレーム、スナップショット 16 枚 × 最大 200 球を id でマージする（O(3000)）。GPU への転送は約 230KB/フレームで、M1 内蔵 GPU なら問題ない。`new` はしない
- **連携（物理）**: `rs−30` のスナップショットが必要。visualOffsetMs=−150 のときは rs が sim.step より約 40 ステップ遅れるので、HISTORY=64 だと足りない。**HISTORY を 96 に上げてほしい**（メモリ増は数十 KB）。足りない場合は描画側で尾を短く切って対処する

## 2. 衝突の余韻を「打点から線全体へ広がる光」にする
- **狙い**: 今は線全体が一様に光るので、どこに当たったかがわからない。光が打点から両端へ走ると「弦が鳴った」ように見えて、音と光のつながりが強まる。投影で遠くから見ても打点がわかる。
- **仕様**（u = 線上の位置 0..1、L = 線の長さ、t = 経過秒数、v = velocity）
  - 打点: `u_hit = 0.5 + ((x−cx)cosθ + (y−cy)sinθ)/L`。θ は hit.step 時点の角度で、[0,1] にクランプする
  - 線全体: `idle + (0.5 + 0.8v)·e^(−t/0.18)`（現行の 1.2+1.8v から下げる）
  - 打点の光: `(1.5 + 2.5v)·e^(−t/τ)·exp(−d/σ(t))`。d = |u−u_hit|·L [px]、`σ(t) = 6 + 500t` [px]、τ = 0.25s
  - 白寄せ: 打点の近くだけ `0.35·e^(−t/0.06)·exp(−d/6)`
  - 端点キャップの色は、同じ式に u=0 と u=1 を入れて CPU で計算する
  - （任意・GUI で切替）弦の揺れ: PlaneGeometry(1,1,24,1) の頂点を法線方向に `2.5v·e^(−t/0.12)·sin(πu)·sin(2π f t)` px ずらす。f = 12 − 0.4·note Hz（低い音ほどゆっくり揺れる。60fps でエイリアスしない範囲）
- **変更箇所**: render.ts の `lines` を、onBeforeCompile で拡張した MeshBasicMaterial にする。インスタンス属性 `aHit = (u_hit, t, v, L)` を追加し、`consume` の hit 分岐で u_hit を計算する。`drawLines` / `putLine` では毎フレーム t を書き込む。加算合成と HDR の方針は今のまま
- **性能**: draw call は増えない。属性は 256×16B、フラグメントの計算は exp 2 回だけ。揺れを有効にしたときの頂点数は 256×50 程度
- **連携（音）**: τ を音の減衰に合わせたい。**音程ごとの release / decay 時間を教えてほしい**（低音ほど長いなら `τ = 0.2 + 0.015·(15−note)` のように音程で変える）。物理側の変更は不要（hit の x, y で足りる）

## 3. 右クリック前のホバー予告と、線の削除アニメーション（ステップ1で省略した分）
- **狙い**: 線が一瞬で消えるのは、この作品の「ゆるやかさ」と合わない。消す前にどの線が消えるかを示し、消えるときは余韻を残す。
- **ホバー**
  - ドラッグしていないとき、pointermove ごとに半径 12px 以内で最寄りの線を `input.hoverId` に入れる（判定は既存の erase と共通にする）
  - 描画: `hoverAmt += (target − hoverAmt)·(1 − e^(−dt/0.05))`。強度は `max(現在値, 0.3 + 0.3·hoverAmt)`、太さは `3 → 3 + 1.5·hoverAmt` px
- **削除**
  - `segmentRemoved` を renderStep で受けたら、その線を `dying` Map に移す（Segment の参照と、e.step 時点の角度 θ を固定して保持する）
  - p = (rs − step)/HZ/0.2 として、強度 `0.8·(1−p)²`、長さ `×(1 − 0.1·easeOutCubic(p))` で中心へ縮め、p≥1 で消す
  - clear（C キー / clearSegments）は、線ごとに `delay = 0.15·cx/1920` s ずらし、0.3s かけて左から右へ拭うように消す
- **変更箇所**: input.ts（`hoverId` と pointermove 時の判定）、render.ts（`dying` Map、`consume` の segmentRemoved 分岐、`drawLines`）、`Preview` 型か render 引数に hoverId を追加。lines の上限は 512 に引き上げる（clear 直後に新しい線を引いたとき用）
- **性能**: ほぼ増えない（ホバー判定は線 256 本 × 点と線分の距離計算 1 回）
- **連携**: 不要。物理側は即座に消える（当たらない）が、見た目は 0.2s でフェードするだけなので矛盾しない。削除時に音を付けるかどうかは D4（衝突の音と光を 1:1）の範囲外なので、main の判断に委ねる

## 見送り・保留
- **ルートやコード変更に合わせた全体の色味変化**: 音担当の提案を待つ。採用する場合は、背景は黒のまま、発光要素の色相だけを 4 小節かけて ±15° 以内でずらす（palette.ts の noteColor に `hueShift` を足す）
- **放出口の見せ方**: 次の放出までを示すカウントダウン弧 `arc = 2π·(1 − 残りステップ/periodSteps)`。1〜3 の後で余裕があれば実装する
